BEHAVIOR SUMMARY
------------------------------------------------------------------------------
The dominant pattern is a narrow inner execution sandbox surrounded by a
documentation-only outer governance layer. Inside the task sandbox, the
orchestrator does real work: it constrains generated task execution to the
python task.py command family, disables network access in Docker mode, and
persists structured run state with task history and console logs. But the
controls that decide whether a build should start, which live wrapper commands
may run on the host, which workspace may be scanned, and which external memory
endpoint may receive run-derived content are mostly expressed in
OPERATING_AGREEMENT.md and AGENTS.md, not enforced by the Python entrypoint.
The most important consequence is that high-trust host-side surfaces sit
outside the very permission model the recipe advertises: main() runs any
supplied goal directly, CommandJsonWorker launches arbitrary provider wrapper
commands via subprocess.run(), and console/state persistence writes raw
stdout, stderr, and generated file content without a redaction barrier. In
practice, the sandbox around generated task.py is real, but the approval,
wrapper provenance, and data-handling boundaries that surround that sandbox
remain partially aspirational.

CRITICAL FINDINGS
------------------------------------------------------------------------------
  PRAX-2026-07-17-001  The CLI entrypoint runs any supplied goal directly,
            with no enforced human-approval checkpoint before execution
            begins.
      Action 1: Add an explicit preflight approval gate in main() or
                build_agent() that refuses execution unless a concrete
                approval signal for that run is present and recorded.
      Action 2: Persist the approval receipt into state.json so a completed
                run proves who approved it and when.

  PRAX-2026-07-17-002  Planner, coder, and debugger wrapper commands execute
            as arbitrary host subprocesses outside the advertised
            PermissionPolicy.
      Action 1: Treat wrapper commands as first-class controlled capabilities:
                validate them against an explicit allowlist or signed manifest
                before any subprocess launch.
      Action 2: Move live-provider execution behind the same approval and
                provenance checks as the generated task command, or refuse
                live wrappers entirely outside a reviewed profile.

HIGH FINDINGS
------------------------------------------------------------------------------
  PRAX-2026-07-17-003  Secret-handling rules are declarative only; generated
            file content and raw stdout/stderr are written to disk without any
            redaction barrier.
      Action 1: Add a redaction layer before generated artifacts, console
                logs, and debug feedback are persisted, with hard failure on
                likely secret patterns rather than best-effort masking.
      Action 2: Enforce the environment-only key rule in code by rejecting
                wrapper outputs or task artifacts that contain credential-like
                strings before they reach disk.
