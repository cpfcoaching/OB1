Coordinating Claude and Codex

How work is split between the two agents, and how it routes through the orchestrator harness.

Handshake: Verified Mode: Mock workers (live not yet wired) Harness: OB1/recipes/master-agent-orchestrator/master_agent.py Date: June 27, 2026

I reached out to the orchestrator and ran a full coordination loop. Claude planned the work, the orchestrator handed each coding task to Codex's lane, the sandbox executed all three, and a lesson was written back to memory. The pattern works. This page is the operating agreement for who does what.

The division of labor

The split is not improvised, it is enforced by the harness's capability registry. Each agent can only call the tools in its lane.

Claude Reason, plan, review, debug

Read-only and judgment work. Never writes or executes code directly.

  • create_task_list — turn a goal into ordered subtasks
  • delegate_to_codex — select one bounded task and hand over context
  • approve_and_proceed — approve a passing result and advance
  • debug_error — read exact stderr, diagnose, return focused feedback

Codex Generate & execute code

Builds artifacts inside the sandbox. Never plans the overall goal.

  • write_file — produce a new file in the task sandbox
  • patch_code — revise an artifact after Claude's debug feedback
  • run_terminal_command — run an approved command in the sandbox
Codex's tools are all policy_checked: the permission policy allows only an approved command set (by default just python task.py). Anything that writes to or mutates an external system needs an explicit, documented approval before it is added.

Where to split work in practice

Kind of workOwnerWhy
Strategy, positioning, content, advisory judgment, prioritizationClaudeReasoning and taste, no code execution needed. This is the chief-of-staff and CPF advisory lane.
Breaking a fuzzy goal into an ordered build planClaudecreate_task_list is Claude's job; Codex never sees the whole goal.
Writing scripts, MCP tools, recipes, schema/migration codeCodexBounded code generation into the sandbox via write_file. This is the "route new tools here instead of hand-rolling" path.
Running tests, executing a build, capturing logsCodexrun_terminal_command under the permission policy.
Reading a failure and deciding the fixClaudedebug_error turns stderr into a focused instruction; Codex then patch_codes.
Approving a result and advancing the workflowClaudeapprove_and_proceed, the human-style review gate.

Rule of thumb: if the task is "decide what and why," it is Claude. If it is "produce or run an artifact," it is Codex. The orchestrator owns state, permissions, retries, and memory so neither agent has to.

To go live (currently mock mode)

The handshake ran with mock workers because no live provider wrappers are attached and Docker is not present in this environment. Three things move it to real Claude + Codex execution:

  1. Provide the Docker sandbox imageSo Codex's generated code runs isolated, not on the host. 
    docker pull python:3.12-slim
  2. Attach the provider wrappersSmall commands that read JSON on stdin and write JSON on stdout. Claude drives planner and debugger, Codex drives coder.
    python3 master_agent.py "your goal" \
  --planner-command  "./workers/claude-plan" \
  --coder-command    "./workers/codex-code" \
  --debugger-command "./workers/claude-debug" \
  --sandbox docker \
  --run-root runs/live
  3. Point memory at the shared OB1 Agent Memory APISo lessons are shared across machines and runtimes, not stuck in one local JSONL.
    python3 master_agent.py "your goal" \
  --openbrain-memory-endpoint "https://YOUR_REF.supabase.co/functions/v1/agent-memory-api" \
  --openbrain-memory-key "$OPEN_BRAIN_MCP_ACCESS_KEY" \
  --openbrain-workspace-id "openbrain" \
  --openbrain-project-id "master-agent-orchestrator"
Keep provider API keys in the wrapper environment only, never in command arguments, generated code, state files, or logs. Expand the permission policy one command at a time, with a documented reason and audit note for each.
